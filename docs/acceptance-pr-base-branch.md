# 关联 PR 合入非默认分支时怎么验：两个方案的对比

> 状态：已定（2026-11-10），采用方案 b。来源：总 issue #378，子 issue #379（临时防护）、#380（长期口径与兜底）。
> 运维怎么处理见 [`acceptance-operations.md`](acceptance-operations.md)「关联 PR 的目标分支（长期口径）」一节。

## 问题

验收轮的代码是宿主按默认分支检出的（`host/prefetch.mjs` 固定取 `refs/remotes/origin/main`）。feature PR 先合进集成分支（`integration/…`），整阶段手测通过后才用一个阶段 PR 合回默认分支。这时按默认分支验，会把还没进默认分支的改动判成「要修」，再开一张修正子单，整条链都是误报。

## 两个方案

- **方案 a：按关联 PR 的目标分支检出代码验。** 合进 `integration/x` 的任务就检出 `integration/x` 来验。
- **方案 b：等合入默认分支再验。** 关联 PR 的目标分支不是默认分支就先不验（`base-not-default`），合入默认分支后自动恢复；超过 3 天还没合入的进每日汇总，由人决定。

## 对比

| 维度 | 方案 a：按目标分支验 | 方案 b：等合入默认分支再验 |
|---|---|---|
| 误报 | 集成分支上的代码验成「通过」后，合回默认分支时可能和别的改动冲突、行为变了，这次「通过」不再成立；修正 PR 只能合回默认分支（写闸拦其它 base），「要修」之后的修正链路接不上 | 不会把还没进默认分支的改动判成「要修」 |
| 漏验 | 少：合进集成分支就验 | 集成分支被放弃、或合回默认分支的 PR 不引用这些 issue 时，任务永远不验。用「超过 3 天进每日汇总」兜底，由人处理 |
| 实现范围 | 盘点、触发判定、预取检出、轮次评论、修正轮的 base、写闸放行的 base、看板显示，约 5～8 处，都在验收机最敏感的路径上 | 触发判定加一道判断（#379），加一个只读汇总步骤（#380），不改检出、不改写闸 |
| 重复验 | 同一任务在集成分支验一次，合回默认分支后还得再验一次（代码变了），两套结论可能互相矛盾 | 只在默认分支验一次 |
| 多 PR、混合 base | 一个任务关联多个 PR、分别合进不同分支时，没有干净的「该检出哪个」答案 | 只看「有没有合入默认分支的 PR」：有就按默认分支验，没有就等 |
| 写闸与点数 | 写闸要放行非默认分支上的读写和修正 PR，每拍多读分支信息 | 不新增 GitHub 调用，盘点请求数不变（新字段都是标量/单对象） |
| 回滚 | 集成分支合回默认分支后通常会被删，回头重验会失败 | 回滚只是撤掉判定，不留状态 |

## 推荐与理由

采用方案 b。按目标分支验带来的问题（结论互相矛盾、修正链路接不上、集成分支删除后无法重验、改动面大）都比「晚几天验」更难处理；方案 b 的代价是漏验，用每日汇总兜底，并且合回默认分支后自动恢复，不需要开关和人工清状态。

## 已知后果

- 非默认分支上的后续合并（包括「要修」之后的修复 PR）不会自动复验，合回默认分支后才一起验。
- 子 issue 在盘点里都是已关闭的，不单独进汇总；被子 issue 拦住、还开着的总 issue 会进。
